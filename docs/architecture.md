# Architecture

## Problem framing

Potree is strong at rendering large, prebuilt spatial hierarchies in the browser, but it is not a
live mutable point cloud database. This project should therefore treat Potree as either:

- a viewer that consumes periodically published snapshots, or
- a codebase to borrow viewer ideas from while we define our own live transport and chunk model.

The first target is **not** a full SLAM backend. The primary use case is that a client device or
upstream service already computes pose/odometry and emits point data in a known frame, while this
server handles persistence, chunking, replay, and visualization.

## Recommended first architecture

### 1. Ingest layer

The server accepts a stream of:

- negotiated session identity metadata
- pose / odometry updates from the client
- point batches already generated by the client
- optional color / intensity metadata
- sensor / publisher identity metadata

Likely transports:

- WebSocket for browser tools and v1 publishers
- optional gRPC later for native high-throughput publishers or internal services

The ingest contract should assume:

- the client is authoritative for pose updates in v1
- the server may reject malformed or out-of-order updates
- a session ID groups all updates for a recording or mapping run
- the server may support resume/reconnect semantics keyed by session ID

### Session model

An initial session should likely contain:

- `session_id`
- `publisher_id`
- `started_at` / `last_seen_at`
- frame convention metadata
- optional project / site / room metadata
- ingest sequence counters for ordering and resume

This makes it possible to persist multiple recordings independently and reopen or append to an
existing world model intentionally.

### 2. Fusion layer

Server-side processing is responsible for:

- transforming incoming points using client-supplied pose/odometry into the session world frame
- rejecting obviously invalid samples
- deduplicating or downsampling repeated observations
- tracking confidence / timestamp / source metadata per chunk

This layer is where drift handling, re-observation policy, and out-of-order message handling will
matter most.

### 3. Mutable spatial store

Instead of writing directly into a Potree octree, persist data in mutable spatial chunks. Good early
options are:

- voxel blocks keyed by 3D grid index
- octant chunks with append/compact cycles
- chunk manifests backed by object storage plus a metadata database

The live store should be the system of record. Potree-compatible output should be a derived product.

### 4. Serving layer

Expose two data products:

1. **Live updates** — chunk deltas or chunk replacement messages for connected viewers.
2. **Static snapshots** — periodically published point cloud representations for fast initial load,
   archival, export, and offline inspection.

### 5. Viewer layer

The viewer should render:

- a static base snapshot for quick startup
- a live overlay fed by the streaming API

That approach avoids forcing full static rebuilds for every incremental update while keeping browser
startup performant.

## Suggested first milestone

The fastest path to a working proof of concept is:

1. Define a session model, chunk schema, and live ingest API.
2. Build a backend that stores and republishes mutable chunks.
3. Start with a simple browser viewer that renders live chunks directly.
4. Add Potree snapshot export once the live data model is stable.

This de-risks the backend before committing to Potree-specific storage decisions too early.

## Stretch goals

- Direct sensor adapters that publish into the ingest API without a separate client pipeline
- Server-side pose estimation / SLAM integration for sensors that cannot provide stable odometry
- On-the-fly registration refinement and loop-closure-aware remapping

## Open design questions

- What scanner(s) are the first ingestion targets?
- Should sessions be append-only, or should we support explicit correction/rewrite operations?
- Is the persistence target room-scale, building-scale, or larger?
- Do we need raw frame retention, or only fused world-state retention?
- Should the first live viewer be Potree-augmented, or a simpler Three.js-based prototype?
